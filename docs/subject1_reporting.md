# 科目一成果上报

参赛队名：北方自控智群队。

任务发布端进入网页 → 科目一成果上报 → 选择已回传任务，或选择整理好的 JSON 文件 → 生成并校验 → 下载核对 → 确认上报赛事方。

接口：`POST http://192.168.1.199:8001/api/v1/public/recognition-results`，免登录，不发送 AuthToken / PeerToken。请求采用 `multipart/form-data`，唯一文件参数名为 `file`，文件名 `target-submission.json`，UTF-8 编码。

坐标为 WGS84 `[经度, 纬度]`。固定目标使用 Point 和 timestamp；移动目标使用 LineString、trackPoints、trackStartTime、trackEndTime，至少两个轨迹点。时间含 ISO 8601 时区，类型型号使用 targetType / targetModel。

附件说明的 Array[3] 与示例二维坐标不一致；按附件 JSON 模板及“经度、纬度”的明确说明提交二维坐标。动态示例中的 vehicleModel 按正式字段表和 JSON 模板统一为 targetModel。

任务发布端将本次启动后的成果放在 `received_images/年-月-日_时-分-秒_微秒/`。其中 `UAV1`～`UAV6` 存放各机原始 JPG 和同名目标 JSON；`subject1_submissions/<任务编号>/` 存放持续更新的 `target-submission.json`、`images/`、`raw-targets.json`、`dedup-decisions.json` 和 `submission-format.json`；`subject1_reports/` 存放冻结的上报 JSON、人工导入的整理记录和赛事接口回执。上报状态接口会返回本次成果目录。

仅任务发布端汇总各终端在本次程序启动后收到的新回传；首次发现某个任务的新文件时，会补齐该任务在对端已有的文件。旧任务若没有新回传，不会自动进入本次成果目录。同一 mission_id 内先按无人机编号和目标 ID 独立整理，再按下述规则进行同机和跨机去重。原始 JSON 和图片始终保留。

## 当前去重与数量规则

1. **首次分类与动静复核。**同机同 ID 按机载接收反馈顺序确定首次属性；动静属性以首次回传的 `is_moving` 为准，不根据 `solider3` 等类别名、类别编号或赛事 `targetModel` 覆盖该标记。首次为静目标时，后续仍整条覆盖、取最后一次信息；首次为动目标时，后续静目标点也纳入轨迹，再进行低速复核。不同飞机的同 ID 仍先独立整理；同机不同 ID 和跨机目标统一按以下距离、轨迹规则判重。

   **低速转静态：**用有效 WGS84 位置和换算后的 `localization_time` 计算相邻观测区间的平均速度。末段各区间都低于4 km/h（约1.111 m/s），累计跨度达到15秒，按静目标上报；恰好4 km/h仍视为移动。检查完整观测历史后才对动轨迹截取最早40点，不能用首尾净位移掩盖高速折返。相同定位时间只取最后回传，不重复计时；只有一个定位、仅等待未收到新定位，不触发转换。后续重新出现达到阈值的运动区间时重新复核。样本间隔较大时这只是观测均速判据，不能证明间隔内完全没有运动，审计以 `sparse_observations` 和最大间隔注明。

   **转换后的字段：**坐标、定位时间、类别、置信度、质量和图片全部取最后一次回传记录，输出 `Point` 和“固定”，不保留 `trackPoints`。最后一条无图片时不借用旧图片；最后一条定位无效时暂不纳入正式文件。原始消息、JSON、图片始终不改。
2. **类别大类。**优先按程序 B 的 `category`：`人→人员`、`车→车辆`、`建筑物→工事`。缺失时沿用旧类别映射。同大类不同具体型号可以判重，例如车辆1与车辆7。正式赛事 `targetType/targetModel` 继续按已有类别编号和型号协议转换；与大类矛盾时保留原始字段并在类别审计中注明。
3. **静动互不合并。**静目标只与静目标比较，动目标只与动目标比较。人员与人员、车辆与车辆、工事与工事用10米阈值；动目标的人员与车辆也用10米；其他组合用5米。每个合并组内的每一对结果都须满足自己的阈值，不能靠连续相邻关系串成大组。
4. **动目标还需轨迹相似。**两条轨迹各至少2个有效点、时长至少3秒，尝试±3秒整数时间偏移；重叠至少3秒且达到较短轨迹的一半。在重叠段比较9个插值位置，至少8个位置在适用阈值内、全部不超过该阈值2倍；两段首尾位移均超过5米时方向余弦至少0.7。有效机地时间参考先用于定位时间换算。不会拼接不同飞机轨迹。
5. **选择代表。**静目标按跟踪定位成功、识别次数更多、原检测分数更高选代表；动目标先比较有效点数（最多按40点计），长度相同再按上述质量顺序选择。每条最终动目标轨迹最多保留按定位时间排序的最早40点。
6. **足量上报16个。**有效候选达到16个时，去重后多于16个按质量保留前16；去重后不足16个，从被合并的真实候选中按质量补足16。再次统一排序并编号。补入的可能是已判同一真实目标的候选，这是为满足操作员要求保留的数量策略；不生成虚构坐标或目标。有效候选不足16个时只上报实际去重结果。目标数按各机有效目标ID算，不按回传消息数、轨迹点数或 `detection_count` 算。缺少合法定位/时间、动轨迹不足两个有效点等记录不能用于凑数。

`dedup-decisions.json` 的 `motion_reclassifications` 记录低速转静态依据，`merged[].same_uav` 标明同机合并；`submission-format.json` 的 `motion_classification` 记录首次标记、最终分类、规则、观测时长、速度和采样间隔。地面日志记录转静态及同机合并数量。

`dedup-decisions.json` 保存原始候选数、去重后数、最终数、合并依据、质量顺序、轨迹截断和 `backfilled` 补入清单；`submission-format.json` 保存同版 `deduplication` 摘要及 `category_records`、`motion_classification`。冻结上报时这些审计继续保存，正式赛事 JSON 不增加内部字段。手动导入同样执行整理，已补满16的旧文件重新导入也保留16个真实候选。

上传的是生成并核对后的固定文件，不会在确认上报时重新生成。无有效目标、字段不符、XYZ 未转换为有效 WGS84 或轨迹不足时会提示；未进入文件的目标数量需人工核对。

选择已回传任务只包含本机已经收到或同步到的同一 mission_id 结果，不代表六架无人机都已回传完毕。未自动合并不同任务，不自动重复上报。HTTP 成功响应仅表示接口已响应，业务是否受理以赛事回执为准；超时先向赛事方确认是否已收到。

此接口未提供图片上传，imagePath 不会上传对应图片。图片保存在本地提交包的 images 目录，待赛事方明确图片提交方式。

本次去重与归档由统一启动入口 `tools/start_ground.ps1`（含 `智信竞赛.exe`）启用，只涉及地面端；旧的 `tools/start_competition_backend_tcp.ps1` 直启方式尚不启用本次按启动时间归档。六台地面电脑都应更新后再进行跨机同步。未向赛事地址发送测试数据。

新版回传字段、类别映射和去重规则见 [completed_targets 协议](completed_targets_protocol.md)。子区域话题见 [任务子区域协议](task_region_protocol.md)。

## 赛事编号、型号与本地整理记录

正式文件在去重、质量排序和最多16个目标筛选完成后，依次使用 `target-001`、`target-002`…作为 `features[].id`。每次生成按本次最终顺序编号；原始机载目标 ID 不修改。`submission-format.json` 的 `id_mapping` 保存源 ID 与赛事 ID 对照，源 ID 重名时结合 `raw-targets.json` 和 `dedup-decisions.json` 查看机号与合并记录。冻结上报文件旁的 `<摘要>.format.json` 保存对应整理记录；摘要绑定正文，避免混用其他版本。

赛事 `targetModel` 将“运动的人员1～4”转换成“人员1～4”，`targetType` 为“人员”、`targetCategory` 仍为“移动”。内部识别类别和机载话题不改。图片路径继续指向真实文件，不因赛事目标编号转换而失效。

`indoorTargets` 是早期程序自定义的排除记录，不是赛事模板字段，实际还可能包含轨迹不足的目标。正式 JSON 不再包含该字段；未进入赛事结果的源 ID、原因及局部坐标保存在 `submission-format.json` 的 `excluded_targets`，原始回传 JSON/JPG 仍保留。人工导入旧文件时同样移出该字段，网页继续显示未纳入数量。

## 目标定位时间与机地时差

静目标的 `timestamp` 和动目标每个 `trackPoints[].timestamp` 都表示外部程序 B 的 **`localization_time` 对应的定位发生时刻**。先换算到任务发布端 Windows 的时间基准，再进行轨迹排序、跨机去重和赛事格式整理，输出北京时间 ISO 8601，例如 `2026-10-09T14:00:00.123+08:00`。

不修改 Windows 或机载系统时间，不在三个程序启动前校时，也不在飞行或重连时跳变时钟。网页保持原布局；比赛用时的编辑不改变目标时间基准。

### 自动只读采样

- 机载图片回传节点从启动起观察 ROS、系统时间和本次开机的单调时钟。收到目标结果时，将定位时刻对应的单调时间、开机标识、时钟段及有效性写入原始 JSON 的 `localization_clock`。原始 `localization_time` 和 ROS 消息不变，程序 B 不需要修改。
- 仅任务发布端采集时间参考。新版通过已经认证的常驻机地 TCP 链路只读采样；其他飞机经对应地面端转发同一探针，不建立新的 SSH 连接。仅旧版机载端不支持 TCP 探针时才使用精简的 SSH 探针（兼容退路，仍可能因 SSH 超时失败）；全部以**发布端 Windows 时间**计量，其他地面电脑的时间不会作为基准。
- 新连接后后台开始采样；稳定连接每30秒刷新，失败后约5秒重试，每机取三次中往返最快的一次。TCP 探针独立于飞行动作队列，不刷新飞控遥测新鲜度，不重启任何程序。往返超过2秒、采样期间 Windows 跳时或机载重新开机时不采用。采样失败不阻塞任务分派、起飞、图片或原始 JSON 回传。
- 换算公式：`定位事件北京时间 = 发布端参考时刻 + (定位事件的机载单调时间 - 参考样本的机载单调时间)`，最后格式化为 `+08:00`。不得使用图片时间、接收时间或上传时间代替定位时刻。

### 重连、补传与历史数据

- 补传沿用第一次保存的时间证据，不因几分钟后收到文件而改变定位时刻。参考按本次机载开机标识匹配，禁止套用其他无人机或其他开机的参考。
- 机载 ROS/系统时间相对单调时间跳变超过250毫秒时重新分段；仿真时间、早于已观察时钟段、未来定位时间、回拨后归属不明等记录标为不能换算。
- 新版记录缺少对应参考或证据无效时，保留原始 JSON/图片，暂不纳入正式目标或有效轨迹点；取得可用参考后自动重新整理，包括之前因 `missing_boot_reference` 暂排除的文件；未重新开机且在24小时内可以用后续参考还原。飞机若已经重新开机，不能拿新开机参考换算旧开机记录，须找到旧开机保存的参考，不能把接收时间替代为定位时间。定位事件与参考相距超过24小时也不推算。
- 旧版没有 `localization_clock` 的记录无法证明机地时差，只能沿用原始合法 `localization_time`，审计明确标为 `unverified_legacy`，不声称已经校准；缺少或为零、格式错误、1970年等明显错误日期仍不进入正式文件。无法从旧文件准确还原的时间不补造。
- `timestamp/image_stamp` 继续匹配相机图像，2秒替代图片的时间记录在 `selected_image_stamp`；与定位时间换算互不代替。
- 手动导入按赛事格式整理的 JSON 保留文件提供的事件时间。`metadata.createdAt` 是生成文件的时间，继续以 UTC `Z` 表示，与定位事件时间不同。

### 查看记录

在本次 `received_images/年-月-日_时-分-秒_微秒/` 下：

- `time_references.json`：按机载开机标识保存的发布端时间参考、无人机编号和采样误差。
- `UAVN/<任务编号>/*.json`：未改写的原始定位时间、图片时间及 `localization_clock`。
- `subject1_submissions/<任务编号>/submission-format.json`：`target_time.records` 保存逐条换算前后值、采用的参考和未换算原因；含已换算、等待参考、旧版未校验的数量。
- `subject1_reports/<摘要>.format.json`：与冻结上报文件绑定的同一份时间审计。

地面会话日志记录参考采样成功/失败及赛事文件整理情况；`/api/v1/status` 的 `target_time_reference` 可查看逐机诊断。原始图片与目标 JSON 仍正常保存于各机目录。诊断额外记录探针链路 `task_tcp` / `ssh_legacy`、采样误差、开机标识和重整结果。此次需同时更新各地面端与机载竞赛代码；程序 B 和系统时钟不修改。

**地面端和竞赛机载端都需要更新**，继续使用 README 的部署命令。此项不增加 ROS 消息字段，不需要修改或重新构建程序 B。

绝对准确性仍取决于发布端 Windows 本身的时间是否正确，以及 B 的 `localization_time` 是否使用机载 ROS 时间。记录的采样误差是所选网络往返的一半加机载读取误差，不包含 Windows 自身误差、源时间误差和长时间离线的时钟漂移；毫秒格式不表示毫秒级绝对精度。

本次15秒低速复核及同机去重更新仅作用于地面结果整理；重启更新后的地面后端生效，无需为此更新机载端或程序 B。旧的冻结上报文件保留原样，需重新生成新版本再核对。
